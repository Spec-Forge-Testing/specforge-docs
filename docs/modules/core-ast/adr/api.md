## ADR-042 — The handler is identified in three steps, and the file can change on the way { #adr-042 }

**Status:** accepted · `api.py`

### Context

The locator answers *which file*. Which function inside it is a separate
question, and the contract seems to answer it: `operationId` is right there.

It does not. `operationId` and the function's name in code are independent
conventions, and in real code there is no reason for them to agree — RealWorld
declares `GetTags` for a handler called `get_all_tags`. Trusting it made
`resolve_handler_name` unreachable for any contract declaring an `operationId`,
which is nearly all of them, and the analysis died on
`TargetNodeNotFoundError` with the file correctly located.

### Decision

`_resolve_target` tries three things in order:

1. **The locator already knows.** A route generated by a resource registration
   has no declaration to read, so the strategy that found it also carried the
   handler name ([ADR-011](locator.md#adr-011)).
2. **The `operationId` names something callable in this file.** Not any
   definition — a type with the same name does not count
   ([ADR-021](ast-builder.md#adr-021)).
3. **Infer it** from the route declaration ([ADR-013](locator.md#adr-013)).

Step 3 may return a **different file**: when the declaration points at a
neighbouring module (`get(listing::list_articles)`), the controller is that one
and not the file declaring the routes, so the `ASTContext` is rebuilt on it and
the `LocatorResult` is updated to match.

### Consequences

The `LocatorResult` a caller receives is not always the one the locator
produced — its `filepath` may have been replaced after the fact. The confidence
and strategy still describe how the *route* was found, not how the file was
finally chosen, which is a seam worth knowing about when reading a result.

## ADR-043 — A batch isolates endpoint failures, but not run failures { #adr-043 }

**Status:** accepted · `api.py`

### Context

A contract has twenty endpoints and they are analysed together. Some will fail:
a controller that cannot be located, a handler that cannot be named. Letting the
first one abort the batch means one unlocatable endpoint costs the other
nineteen.

### Decision

`analyze_endpoints` returns one `EndpointAnalysisResult` per endpoint, each
carrying either its analysis or the domain exception that stopped it. The
exceptions it catches are listed in `ENDPOINT_ANALYSIS_ERRORS` — precisely those
that exhaust *one* endpoint and say nothing about the others.

Anything outside that tuple propagates and ends the run: a repository that does
not exist, a missing `.scm` file. There is no partial result worth showing when
the input itself is wrong.

All endpoints share one `ParserManager`, so grammars and trees are parsed once.

### Consequences

The tuple is the contract, and it is easy to get wrong in either direction.
Adding an exception to it turns a broken installation into twenty quiet
failures; leaving one out turns a single bad endpoint into a dead batch.
`SourceFileNotFoundError` was deliberately left out for that reason: a file that
vanished between the scan and the parse is not an ordinary per-endpoint outcome.

`ok` on the result tells the two apart without the caller matching on exception
types.
