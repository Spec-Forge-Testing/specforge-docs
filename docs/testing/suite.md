# Integration suite

Tests **Spec Forge against the real world**: the contracts and APIs of the
two corpora in this repository, never fabricated examples.

One folder per module, and each one tests **from the start of the pipeline
through that stage** with the modules genuinely wired together.
`core_ast/` doesn't test `core_ast` in isolation — it tests contract
parsing + static analysis chained.

```bash
./run.sh                        the whole suite
./run.sh contract_engine        one folder
./run.sh -k realworld -v        any pytest argument
./run.sh --shell                a shell inside, for poking around
```

## The rules

**If it's real, it gets tested. If Spec Forge can't handle it, that's our
problem.** The corpus contracts exist, are published, and are never edited.
A contract Spec Forge rejects is a Spec Forge failure, not a defect in the
corpus and not a case to excuse. That's why **a red test here is the
mechanism working** — it's how you find out what's missing.

**Nothing fabricated.** Testing a function against a minimal hand-written
contract is already what each module's own unit tests do. The value here is
in what a made-up contract never has: 1,497 endpoints, versions from 2.0 to
3.1, generated by different tools, and broken in ways nobody would bother
simulating.

**Entry only through the CLI.** Everything goes through
`specforge_cli.services`, never importing a `lib/` package directly. What's
under test is the pipeline as the product actually uses it, not the
libraries in isolation.

**The CLI wires modules together, not the harness.** If chaining two stages
required writing glue code here, that glue is missing from Spec Forge itself,
and the test would be exercising our own code instead of the product's. A
facade function the CLI doesn't reach **is not tested here** — it gets
flagged as a missing seam instead.

**Nothing installs on the host.** Same as both corpora: everything runs
inside a container.

## How correctness is decided

Every folder has two directories with **the same structure and the same file
names**:

| | What it is | How it's created |
| --- | --- | --- |
| `esperado/` | what the function **should** return | written and reviewed by hand against the contract or the source, once |
| `output/` | what the function **actually** returned | regenerated on every run |

**Expected files are never generated.** If they came from a run they'd be a
snapshot of current behavior: today's bugs would be written down as correct,
and the test would pass while celebrating them. That's why they describe
**what the contract or the code declare**, not what Spec Forge returns. The
difference between the two is the outstanding work.

The test, then, does exactly one thing: run the function and compare its
output against the file. Since both sides come from the same projection
(`salida.py`), they're comparable line by line, and on failure the test
prints the exact command that shows the full diff:

```
AssertionError: diff tests/contract_engine/esperado/extract_endpoints/webgoat.json \
                     tests/contract_engine/output/extract_endpoints/webgoat.json
```

That's needed because pytest's own diff, on a 204-endpoint contract, just
says "the list differs" and truncates.

## Does the API need to be running?

Depends on the stage, and it's what decides how expensive each folder is:

| Stage | Consumes | Live API? |
| --- | --- | --- |
| `contract_engine` | the contract file | No |
| `core_ast` | the contract + source code on disk | No |
| `semantic_inference` | the contract + extracted context | No |
| `custom_schemathesis` | the contract + **a SUT answering** | **Yes** |

The first three are static analysis — `core_ast` reads source code, it never
executes it. That's why today's suite runs offline, in seconds, and the
corpus as checked into the repo is enough.

`custom_schemathesis` breaks that pattern, because fuzzing means sending
requests. It needs a SUT up on `http://localhost:8000` and, if it's from
EMB, compiled first.

### What's missing before that folder exists

**A class for EMB, like the one RealWorld already has.**
[`real-world/corpus.py`](real-world.md#from-python-corpuspy) exposes the 12
implementations from Python: `rw.go()` boots and returns once the API
answers, and leaves `host`, `spec`, `fuente` and `sha` as attributes. EMB
only has `up.sh` and `down.sh` today — see
[EMB → Pending](emb.md#pending-a-python-api).

## How it's built

`Dockerfile` brings in only third-party dependencies. Spec Forge's own code
is **never installed** — it's mounted and reaches the interpreter through
`PYTHONPATH` pointed at each package's `src/`, so changing it never forces a
rebuild. `run.sh` mounts Spec Forge and the corpus read-only — the suite
exercises them, it doesn't modify them — and mounts `output/` read-write,
running as the host user so generated files don't end up owned by root.

`corpora.py` is the catalog of the 37 contracts. Each one's version **is
read from the file itself**, not from a hand-maintained list: adding a
contract to the corpus shouldn't require editing the catalog.

Each `conftest.py` does **a single pass per session**: the 37 contracts are
ingested once, the 12 implementations are analyzed once, and every test
asserts against that shared result. Two consequences: the suite doesn't
repeat the same work 74 times, and what lands in `output/` is a byproduct of
running the tests, not a second pass that could diverge from what was
actually asserted.

There's also a guard in `pytest_sessionstart`: if the corpus doesn't have
exactly 37 contracts, or the RealWorld one is missing, the session refuses to
start. It doesn't test Spec Forge — it tests that the harness is looking at
what it thinks it's looking at.

## Status

| Folder | Covers | Status |
| --- | --- | --- |
| `contract_engine/` | 2 functions × 37 contracts | Run. **27 of 74 red** |
| `core_ast/` | 2 functions × 12 implementations | Written, **not run yet**: inherits whatever the previous stage delivers |

`custom_schemathesis` and `semantic_inference` aren't tested yet: those
stages aren't finished. When they are, each adds its own folder under the
same rule — if the seam doesn't exist in the CLI, it doesn't get written
here.

### `contract_engine/`: 27 of 74 red

**25 contracts fail to load.** 19 are Swagger 2.0 and 6 are OpenAPI 3.x with
their own defects — missing `info.title` or `info.version`, path parameters
used without being declared, or a `$ref` to a `/components` that doesn't
exist. All 25 are real, published contracts, so all 25 are outstanding work.

**2 contracts keep unresolved references**: `familie-ba-sak` (15) and
`spring-rest-example` (6) — without the recursion marker, a deliberate cycle
and a broken reference are indistinguishable to whoever consumes the
contract.

The other 25 test failures are skipped because their contract never loaded —
each problem is counted once, at the stage where it originates.

Two more findings that don't fail any test but came out of these runs: of
the 19 Swagger 2.0 contracts, **only 7 reach the version check** — the rest
die earlier in validation, so the user sees "Validation error" instead of
"Swagger 2.0 not supported" — and `prance`'s `ResolutionError` **reaches the
CLI raw** in 4 contracts, against the repository's own convention.

### `core_ast/`: written, not run

The previous stage is broken for 25 of the 37 contracts, and this one
inherits whatever that stage delivers: reading these results as a measure of
language support doesn't make sense until the contract stage lands cleanly.

What exploration did measure: **today 1 of the 228 endpoints completes** the
analysis. The two causes are not the ones expected going in:

**Routes are fragmented.** Almost every framework builds the final route
from a prefix plus a relative route, so the full path the contract declares
**never appears literal in the code**. In Gin, `/users/login` is declared as
`router.POST("/login", UsersLogin)` inside a group mounted at `/users`; same
story in FastAPI. The locator searches for the full path and finds it
nowhere.

**The path hides behind a named attribute.** `java/spring` does write the
full route — `@RequestMapping(path = "/users/login", method = POST)` — but
the locator expects the route to sit right next to the annotation and
doesn't know to skip over `path = `.

Neither cause has anything to do with a language's grammar or its route
template syntax, which was the prior hypothesis.

## Roadmap

### 1. Stop stage 1 from losing contracts

`contract_engine/` has **27 of 74 red**, and everything downstream inherits
that: `core_ast/` can't be read as a measurement of language support while
the contract isn't arriving intact. This is the first item, tracked in the
Contract Engine epic (AI-198…AI-202).

### 2. Run `core_ast/`

The files are written and all 228 endpoints are mapped by hand. What's
missing is the run itself, which only means something once item 1 is done.

What exploration already measured: **today 1 of the 228 completes**, for two
causes that weren't the ones expected — routes are fragmented (prefix +
relative route, so the full route never appears literal) and Spring hides
the path behind a named `path = ` attribute. Neither is about language
grammar. Detail in [Status → `core_ast/`](#core_ast-written-not-run) above.

### 3. EMB's Python class, before the `custom_schemathesis` folder

The only piece of infrastructure still missing, needed because that stage

### 4. The folders that don't exist yet
